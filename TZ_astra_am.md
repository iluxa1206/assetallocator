> Документ для передачи в Claude Code. Содержит требования заказчика,
> контекст существующего прототипа и план реализации MVP.

## 1. Контекст

Astra AM (Asset Management) — российская инвестиционная компания.
У нас работает HTML-прототип sales-дашборда (`sales_dashboard.html`):
менеджер по продажам вводит сумму инвестиций клиента, выбирает
риск-профиль и валютную стратегию, получает рекомендуемую аллокацию
по фондам с диаграммами, бэктестом и экспортом (PDF / Excel / шаблон
письма).

Прототип — один автономный HTML-файл. Это даёт автономность, но не
решает: централизованное обновление данных, авторизацию, сохранение
работы сейлза по клиентам, доступ с мобильного, мониторинг.

Задача — построить **веб-приложение** (PWA), которое сохраняет всю
функциональность прототипа и добавляет недостающее.

## 2. Зафиксированные требования заказчика

### 2.1. Пользователи и доступ

- **До 100 сейлзов** в перспективе.
- **Три роли:**
  - `analyst` — обновляет данные котировок, редактирует модельные
    аллокации, видит общую аналитику.
  - `sales` — основной пользователь. Подбирает аллокации, сохраняет
    их под клиентами, отправляет предложения, ведёт мини-CRM по своим
    клиентам.
  - `manager` — руководитель отдела продаж. Видит данные всех сейлзов,
    может смотреть их историю предложений и сохранённых аллокаций.
- **Только внутреннее использование.** Клиенты компании в системе
  напрямую ничего не видят. Все клиентские данные внутри системы —
  обезличенные (имя/код клиента — на усмотрение сейлза, без ПДн).
- **Регистрация — собственная** (не SSO, не корпоративный AD).
  Учётные записи создаются вручную администратором или по приглашению.
- **Язык интерфейса:** только русский.
- **География:** только Россия.

### 2.2. Что должен уметь сейлз

- Выбирать параметры портфеля (сумма, риск-профиль, валютная стратегия)
  и видеть аллокацию по фондам и валютам — как в текущем прототипе.
- **Сохранять аллокации под конкретным клиентом** (мини-CRM внутри
  системы). У сейлза десятки клиентов одновременно.
- **Редактировать** ранее сохранённые аллокации и отслеживать их
  результат (как сработала бы предложенная стратегия с момента
  предложения).
- **Отправлять клиенту официальное предложение** (PDF/email).
- **Логировать в compliance-журнал** факт предложения (что, кому,
  когда).
- **Работать с планшета на встрече с клиентом**: открыть мобильное
  приложение, выбрать клиента, подобрать стратегию вживую.

### 2.3. Что должен видеть руководитель

- Все сейлзы и их активность.
- Все сохранённые аллокации по всем клиентам всех сейлзов.
- История предложений.
- Сводная аналитика (по желанию — в более поздних версиях).

### 2.4. Что должен делать аналитик

- Обновлять данные по фондам **раз в месяц** в конце периода.
- Обновлять данные по индексам и курсам с тех же источников.
- При необходимости — корректировать модельные аллокации.

### 2.5. Источники данных

- **Котировки фондов:**
  - Сейчас приходят вручную ежемесячно через Excel.
  - В перспективе — автоматическая подгрузка с
    [investfunds.ru](https://investfunds.ru) (нужна реализация
    парсера/коннектора).
- **Индексы, курсы, инфляция:**
  - Исторический кэш — из Excel (последняя версия в `фонды_111-11.xlsx`,
    лист «Лист2»).
  - Свежие точки — через API Cbonds, MOEX ISS и, при необходимости,
    других источников (уточним при реализации).
- **Частота обновления:** раз в месяц.
- **Глубина истории:** оставляем как есть в исходниках (с конца
  2020 года для CPI, с конца 2021 для большинства фондов).

### 2.6. Compliance

- Обязательное логирование предложений клиентам.
- 152-ФЗ **не критичен**: данные клиентов в системе обезличены,
  персональные данные не хранятся.
- Двухфакторная аутентификация — желательна (добавляем во вторую
  итерацию).
- Шифрование «at rest» — желательно.
- Развёрнутый журнал аудита (каждое действие) — пока не нужен.

### 2.7. Технические ограничения

- **Стек выбираем свободно** — нет привязки к существующим
  IT-стандартам компании.
- **DevOps в компании нет** — нужно ориентироваться на максимально
  managed-решения и простые в обслуживании компоненты.
- **MVP делаем на локальном компе** разработчика, продакшен —
  следующим этапом.
- **Срок MVP:** ~1 месяц.
- **Бюджет:** есть потолок, экономим где можно.
- **Стиль:** современный, минималистичный, в духе существующего
  прототипа (тёмная hedge-fund тема + светлая, переключатель,
  шрифт Gilroy).

### 2.8. PWA — мобильное использование

PWA нужен для трёх сценариев на планшете/телефоне:

1. **Презентация на встрече:** сейлз показывает клиенту экран,
   меняет параметры вживую, обсуждают.
2. **Просмотр сохранённой аллокации** — быстро открыть, что
   предлагалось клиенту X.
3. **Подбор с нуля** с мобильного — тоже должен быть удобен.

**Оффлайн-режим важен** — должна быть кешированная версия данных
на устройстве, позволяющая работать без сети (например, на встрече
с плохим интернетом).

Уведомлений (push) пока не требуется.

## 3. Архитектура MVP

### 3.1. Высокоуровневая схема

```
┌──────────────────────────────────────────────────────────────┐
│                      Браузер / PWA                           │
│  ┌─────────────────────────────────────────────────────┐     │
│  │  Next.js (React + TypeScript)                       │     │
│  │  • UI                                               │     │
│  │  • TS-расчёты для мгновенной интерактивности        │     │
│  │  • Service Worker (next-pwa) для оффлайн            │     │
│  │  • IndexedDB кеш рыночных данных                    │     │
│  └─────────────────────────────────────────────────────┘     │
└─────────────────────────────┬────────────────────────────────┘
                              │ HTTPS, JWT в Authorization header
                              ▼
┌──────────────────────────────────────────────────────────────┐
│              FastAPI (Python 3.12)                           │
│  • REST API v1                                               │
│  • JWT-аутентификация (fastapi-users)                        │
│  • Авторизация по ролям через dependency-injection           │
│  • Эталонные расчёты в Python (источник правды)              │
│  • Парсеры внешних источников (investfunds / cbonds / moex)  │
│  • Генерация PDF (WeasyPrint), Excel (openpyxl)              │
│  • APScheduler — периодическое обновление котировок          │
└─────────────────────────────┬────────────────────────────────┘
                              │
                              ▼
                  ┌──────────────────────┐
                  │   PostgreSQL 16      │
                  │   (через SQLAlchemy) │
                  └──────────────────────┘
```

**Ключевой принцип расчётов:**
- **Сервер хранит и отдаёт сырые данные** (котировки, индексы) одной
  пачкой при загрузке дашборда.
- **Браузер пересчитывает всё локально** (TS-копия формул) при
  движении слайдеров и переключателей — мгновенная интерактивность.
- **Python-формулы — источник правды.** Используются для серверной
  генерации PDF/Excel, для рассылок и как эталон для тестов.
- **TS-формулы синхронизированы с Python через эталонные тесты** —
  один JSON-файл `test_vectors.json` генерируется Python-тестами,
  TS-тесты используют его для проверки совпадения значений.

Это даёт оффлайн-работу из коробки (закешировал данные — пересчёт
работает без сервера) и нулевую задержку UI.

### 3.2. Стек

#### Backend (Python 3.12)

| Компонент | Технология | Почему |
|---|---|---|
| Web-фреймворк | **FastAPI** | Современный, типизированный, асинхронный, авто-документация OpenAPI |
| ORM | **SQLAlchemy 2.0** (async) | Стандарт, отличная типизация в 2.0 |
| Миграции | **Alembic** | Каноничный спутник SQLAlchemy |
| БД | **PostgreSQL 16** | Стандарт для финансовых данных, надёжность |
| Валидация | **Pydantic v2** | Встроено в FastAPI, общие схемы |
| Auth | **fastapi-users** | Регистрация/логин/JWT/восстановление из коробки |
| Расчёты | **NumPy** + **pandas** | Эталон для финансовых расчётов |
| Парсинг Excel | **openpyxl** + **pandas** | Для seed и импортов |
| HTTP-клиент | **httpx** (async) | Для Cbonds, MOEX ISS, investfunds |
| Парсинг HTML | **selectolax** или **BeautifulSoup** | Для investfunds, если нет API |
| PDF | **WeasyPrint** | HTML→PDF, удобно для шаблонов |
| Excel-экспорт | **openpyxl** или **xlsxwriter** | Стандарт |
| Планировщик | **APScheduler** | Встраивается в FastAPI, простой |
| Тесты | **pytest** + **pytest-asyncio** | Стандарт |
| Менеджер пакетов | **uv** или **poetry** | uv быстрее, poetry привычнее |
| Линтинг | **ruff** + **mypy** | Современная связка |

#### Frontend (TypeScript)

| Компонент | Технология | Почему |
|---|---|---|
| Фреймворк | **Next.js 14+** (App Router) | SSR/SSG, отличная поддержка PWA, удобные роуты |
| Язык | **TypeScript** (strict) | Типобезопасность |
| Стили | **Tailwind CSS** | Скорость, единая система |
| Компоненты | **shadcn/ui** | Современно, кастомизируется, не «коробочный» вид |
| Графики | **Recharts** | Декларативно для React; альтернатива — Chart.js (как в прототипе) |
| Состояние сервера | **TanStack Query** (React Query) | Кеширование, инвалидация, оффлайн-persistence |
| Состояние UI | **Zustand** или React Context | Простое локальное состояние |
| Формы | **react-hook-form** + Zod | Валидация |
| Типы API | **openapi-typescript** | Генерация TS-типов из OpenAPI-схемы FastAPI |
| PWA | **next-pwa** | Service worker, кеш, манифест |
| Оффлайн-кеш | **IndexedDB** через **idb-keyval** | Хранение рыночных данных |
| Тесты | **Vitest** + **Playwright** (e2e) | Современная связка |

#### Инфраструктура

| Компонент | Технология | Почему |
|---|---|---|
| Локальная разработка | **Docker Compose** | postgres + backend + frontend одной командой |
| Контейнеризация | **Dockerfile** для backend и frontend | Готово к продакшену |
| Деплой (далее) | **Railway** или **Yandex Cloud** | Managed PostgreSQL, простой деплой |
| Reverse proxy | **Caddy** или **Traefik** (на проде) | Авто-TLS, простая настройка |
| Мониторинг (после MVP) | **Sentry** (ошибки) | Бесплатный план достаточен |

### 3.4. Модель данных (SQLAlchemy 2.0)

```python
# models/user.py
from enum import Enum
from sqlalchemy.orm import Mapped, mapped_column

class Role(str, Enum):
    ANALYST = "analyst"
    SALES = "sales"
    MANAGER = "manager"

class User(Base):
    __tablename__ = "users"
    id: Mapped[str] = mapped_column(primary_key=True)  # cuid/uuid
    email: Mapped[str] = mapped_column(unique=True, index=True)
    password_hash: Mapped[str]
    full_name: Mapped[str]
    role: Mapped[Role]
    is_active: Mapped[bool] = mapped_column(default=True)
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())
    updated_at: Mapped[datetime] = mapped_column(onupdate=func.now())

    clients: Mapped[list["Client"]] = relationship(back_populates="owner")
    proposals: Mapped[list["Proposal"]] = relationship(back_populates="owner")
```

**Сущности (минимум для MVP):**

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `users` | Пользователи и роли | id, email, password_hash, full_name, role, is_active |
| `clients` | Мини-CRM сейлза (обезличенные коды клиентов) | id, owner_id, code, notes |
| `proposals` | Сохранённые аллокации / предложения | id, owner_id, client_id, title, amount, amount_currency, base_currency, risk_profile, currency_strategy, fund_weights (JSON), index_weights (JSON), proposal_date, sent_to_client, sent_at |
| `funds` | Справочник фондов | key (PK), name, native_currency, benchmark, benchmark_label, is_active |
| `fund_quotes` | Котировки паёв | id, fund_key, date, price_rub. UNIQUE(fund_key, date) |
| `market_data_points` | Индексы, курсы, инфляция (одна строка на дату) | date (PK), rusfar, rgbitr, mcftr, cbonds_zo_rub, rucnytr_rub, gldrub, usdrub, cnyrub, cpi_rub_yoy, cpi_usd_yoy, cpi_cny_yoy |
| `allocation_models` | Версии модельных аллокаций | id, version, is_active, data (JSON), comment, created_by_id |
| `audit_events` | Минимальный compliance-лог | id, user_id, action, payload (JSON), created_at |
| `invitations` | Приглашения новых пользователей | id, email, role, token, expires_at, used |

Полная Prisma-аналогичная схема (если нужно глянуть подробности) —
в исходном `status.md` и схожих по структуре полях существующего

### 3.6. Cross-validation расчётов (Python ↔ TypeScript)

**Проблема:** формулы продублированы — на Python (источник правды,
бэкенд) и на TypeScript (для мгновенной интерактивности). При
расхождении могут возникнуть тонкие баги.

**Решение:** `expected_vectors.json` — большой набор тестовых
кейсов, единственный артефакт согласованности.

**Workflow:**

1. **Python-скрипт `scripts/generate_test_vectors.py`** генерирует
   набор кейсов с разными сочетаниями параметров (риск-профиль,
   валюта, период, сумма). Для каждого кейса вычисляются ожидаемые
   значения: ряды портфеля, метрики, FX-декомпозиция, CPI.
   Результат — `expected_vectors.json` (несколько сотен кейсов).
2. **Python-тесты** (`pytest`) проверяют, что Python-функции дают
   именно эти значения — гарантируют стабильность эталона.
3. **TS-тесты** (`vitest`) загружают `expected_vectors.json` и
   проверяют, что TS-функции дают те же значения с точностью 1e-9.
4. **В CI** оба пакета тестов гоняются обязательно. Расхождение —
   красный билд.

Эталон Книга2.xlsx используется для проверки FX-декомпозиции в
`test_fx_decomp.py` — это уже верифицированный заказчиком кейс.

## 4. Модули и функциональность MVP

### 4.1. Аутентификация и роли

- **Логин/пароль** через fastapi-users (JWT, bcrypt).
- **Регистрация только по приглашению.** Аналитик/руководитель
  создаёт инвайт → одноразовая ссылка → новый пользователь
  устанавливает пароль и заходит.
- **Восстановление пароля** через одноразовую ссылку на email.
- Middleware Next.js проверяет JWT в `localStorage` (а лучше — в
  HttpOnly cookie); защищённые маршруты редиректят на `/login`.
- На бэкенде FastAPI dependency проверяет токен и роль; роли
  для каждого роутера явные.
- 2FA — не в MVP, во второй итерации.

### 4.2. Главный дашборд (`/dashboard`)

Полный перенос функциональности из `sales_dashboard.html`:

- Ввод суммы, выбор валюты, выбор риск-профиля, выбор валютной
  стратегии (3 шага).
- Кольцевые диаграммы: аллокация по фондам и распределение по
  валютам (2 сегмента: рубль / валюта, золото в валюте).
- Бэктест: выбор периода и базовой валюты, KPI-карточки (Сумма
  на старте / на конец, финансовый результат, CAGR, max DD).
- Раскрываемые блоки:
  - Историческая динамика (график с тогглами Портфель/Индекс/Инфляция
    + сравнительная таблица параметров).
  - Финансовый результат по фондам.
  - FX-декомпозиция.
- Скрытая панель «Индивидуальный портфель»: ручная настройка долей
  фондов; индексы автоматически следуют за бенчмарками (вариант A).
- Переключатель темы (светлая/тёмная).
- Экспорт PDF / Excel / шаблон письма.

**Поток данных:**
1. При загрузке страницы делается **один** запрос
   `GET /api/v1/market-data/bundle?from=&to=` — все котировки фондов,
   индексов, курсов, активная модельная аллокация.
2. Данные кешируются в IndexedDB через TanStack Query +
   `idb-keyval`. При следующем заходе сразу показываются из кеша,
   фоновый запрос обновляет.
3. Все вычисления (`computePortfolioSeries`, `calcMetrics`,
   `getCurrencyBreakdown`, FX-декомпозиция и т.д.) — на клиенте,
   в TypeScript-копии формул. Это даёт мгновенную реакцию на
   движение слайдеров.

### 4.3. Клиенты (мини-CRM, `/clients`)

- Список клиентов сейлза (с обезличенными кодами/именами).
- Создание клиента — простая форма (код, заметки).
- Карточка клиента: список сохранённых предложений по нему,
  переход к каждому.
- Архивация (soft-delete через `deleted_at`).

### 4.4. Предложения (`/proposals`, `/proposals/[id]`)

- На главном дашборде после подбора аллокации — кнопка
  «**Сохранить предложение**».
- Диалог выбора клиента (из своего списка) или создания нового.
- Опциональный заголовок и комментарий.
- После сохранения — переход на `/proposals/[id]`:
  - Текущие параметры.
  - Кнопка «Редактировать» → открывается дашборд с подгруженным
    состоянием через query-параметр `?from=proposal_id`.
  - **Просмотр фактического результата:** если есть свежие
    котировки, фронт пересчитывает «как сработала бы стратегия с
    `proposal_date` по сегодня». На графике видна предложенная
    стратегия и её фактическая динамика.
  - Кнопка «Отправить клиенту»: генерация PDF на бэке, скачивание +
    запись в `audit_events` (action=`proposal.send`) +
    `proposal.sent_at = now()`.
- Список всех своих предложений с фильтрами (клиент, дата, статус).

### 4.5. Команда (`/team`, для manager)

- Список всех сейлзов с метриками: количество клиентов, предложений
  за последний месяц, последняя активность.
- По клику на сейлза — все его клиенты и предложения.
- Возможность открыть любое предложение в режиме просмотра.

### 4.6. Администрирование (`/admin`, для analyst)

- **Импорт котировок фондов:**
  - Загрузка нового Excel.
  - Парсинг → диффинг с существующими данными → превью изменений
    (новые строки / изменённые значения) → подтверждение.
  - **Автоимпорт с investfunds.ru:** список настроенных фондов,
    кнопка «Обновить с investfunds», прогресс.
- **Импорт индексов и курсов:**
  - Ручной (Excel) или подтягивание из Cbonds / MOEX ISS.
- **Редактирование модельных аллокаций:**
  - Таблица как в `Книга1.xlsx`, инлайн-редактирование.
  - Сохранение новой версии (новая запись `allocation_models`).
  - Кнопка «Сделать активной».
  - История версий с comment-полем.
- **Управление пользователями:**
  - Список, генерация ссылки-приглашения, отключение пользователя.

### 4.7. PWA-функциональность

- **Манифест + service worker** через `next-pwa`.
- Установка как приложение (иконка на главный экран
  телефона/планшета).
- **Оффлайн-режим:**
  - Кеш статических ресурсов (JS, CSS, шрифты).
  - Кеш последнего `market-data/bundle` в IndexedDB при онлайне.
  - В оффлайне доступны: дашборд (на закешированных данных),
    просмотр своих клиентов и предложений (закешированных).
  - Создание новых предложений в оффлайне — очередь в IndexedDB,
    автосинхронизация при появлении сети.
- **Адаптивный UI** для планшетов и телефонов: setup-блок
  сворачивается в 1 колонку на мобилке, диаграммы остаются крупными,
  таблицы — горизонтальный скролл.

## 6. Принципы реализации

1. **Простота важнее модности.** FastAPI + Next.js в Docker Compose.
   Никаких микросервисов, k8s, очередей, шин событий — не сейчас.
2. **Типобезопасность сквозная.** Python: ruff + mypy strict.
   TypeScript: strict. Pydantic v2 для DTO. OpenAPI →
   openapi-typescript для TS-типов API.
3. **Расчёты — чистые функции.** Никакой работы с БД и DOM в
   `calculations/`. Покрыты unit-тестами. Cross-validated через
   `expected_vectors.json`.
4. **Стиль — как в прототипе.** Тёмная hedge-fund тема + светлая,
   шрифт Gilroy, минимализм. Через CSS-переменные.
5. **Mobile-first для PWA-страниц.** Дашборд и просмотр предложений
   тестируются в первую очередь на планшете.
6. **Никаких хардкод-данных в продакшен-коде.** Все справочники
   (фонды, индексы, аллокации) — в БД. В коде — только формулы,
   логика и константы, которые не редактируются (например, ключи
   индексов).
7. **Компонент = одна ответственность.** Большие экранные сущности
   из прототипа выносятся в отдельные React-компоненты.
8. **Server Side Source of Truth.** Python-формулы — эталон.
   TS-формулы валидируются против Python через сгенерированный JSON.
9. **Не оптимизировать преждевременно.** Async везде, где FastAPI
   просит. БД-запросы без преждевременных индексов и денормализации.
10. **Сначала работает, потом красиво.** Каждая неделя заканчивается
    рабочим демо.

## 10. Критерии готовности MVP

- ✅ Сейлз заходит по логину/паролю.
- ✅ Подбирает аллокацию на главном экране — всё как в прототипе.
- ✅ Все 7 модельных портфелей суммируются в 100%, валютная
  экспозиция точно соответствует таблице (50/50, 55/50/45, 60/50/40).
- ✅ FX-декомпозиция совпадает с эталоном из `Книга2.xlsx`.
- ✅ CPI считается по точной YoY-формуле (тест на синтетических
  данных).
- ✅ Сохраняет предложение под клиентом, возвращается через день —
  видит предложение и его текущий результат.
- ✅ Скачивает PDF предложения (внешний вид совпадает с шаблоном).
- ✅ Руководитель видит активность всех сейлзов.
- ✅ Аналитик загружает новый Excel с котировками — после
  подтверждения все сейлзы видят актуальные данные.
- ✅ Приложение открывается на планшете, устанавливается как PWA,
  работает оффлайн (на закешированных данных).
- ✅ Внешний вид — не хуже прототипа.
- ✅ Python-тесты и TS-тесты дают совпадающие значения для всех
  ~200 кейсов из `expected_vectors.json`.
